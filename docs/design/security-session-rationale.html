로그인 보안: 왜 세션 방식인가,
왜 리프레시 토큰을 쓰지 않았나

웹(선생님) + Electron 데스크톱 앱(학생) · Spring Boot 4 · Spring Session(Redis)

작성 2026-11-16근거: IETF RFC 10017 · RFC 9700 · OWASP실측 검증 포함
한 줄 결론 — 리프레시 토큰을 쓰지 않은 것은 임시방편이 아니라, IETF 표준(RFC 10017)이 브라우저 앱에서 가장 안전하다고 권하는 BFF 패턴을 따른 결과다. 토큰은 서버에만 두고 클라이언트에는 HttpOnly 세션 쿠키만 준다. 세션은 OWASP 기준으로 보호했고, 남은 보완점 2가지(시간 제한)도 명시한다.

1. 우리 구조 = 표준이 "가장 안전하다"고 한 BFF 패턴

IETF의 브라우저 앱 OAuth 표준(RFC 10017, 초안 draft-ietf-oauth-browser-based-apps의 최종판)은 로그인 구조를 안전한 순서대로 나열하고, 그 첫 번째인 BFF(Backend For Frontend)를 업무용 앱에 강하게 권한다.

"토큰은 BFF에만 있으므로 브라우저에서 빼낼 토큰이 없다."RFC 10017 (draft-27) 6.1절 — "Since tokens are only available to the BFF, there are no tokens available to extract from the browser"

2. 리프레시 토큰을 쓰지 않은 근거 3가지

1표준의 무거운 의무

클라이언트(브라우저·데스크톱 앱)에 리프레시 토큰을 주면 RFC 9700에 따라 회전 또는 발신자 제한이 필수. 우리는 토큰을 주지 않으므로 의무 자체가 없다.

2브라우저 보관 위험

OWASP는 세션 식별자를 localStorage에 두지 말라고 명시. JWT는 화면 코드가 들고 있어야 해 XSS에 노출된다. HttpOnly 쿠키는 화면 코드가 읽을 수 없다.

3즉시 차단 필요

세션 제외 · 계정 정지가 바로 반영돼야 한다. JWT는 만료 전 취소가 어렵고, 그 보완책이 리프레시·차단 목록. 세션은 Redis에서 지우면 즉시 끝.

"공개 클라이언트의 리프레시 토큰은 반드시 발신자 제한을 하거나 리프레시 토큰 회전을 사용해야 한다."RFC 9700 (2025.1) 2.2.2절 — "Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation"
"세션 식별자를 localStorage에 저장하지 마라. 데이터가 항상 JavaScript로 접근 가능하다." / "쿠키는 httpOnly 플래그로 이 위험을 줄일 수 있다."OWASP HTML5 Security Cheat Sheet
"웹 애플리케이션은 최소한 서버 쪽에서 세션을 무효화해야 한다." / "쿠키만 지우는 것으로는 훔쳐 간 세션 사본이 무효가 되지 않는다."OWASP Session Management Cheat Sheet

JWT + 리프레시 토큰을 도입했다면 생겼을 비용

항목세션 쿠키 (채택)JWT + 리프레시 (미채택)
로그아웃 · 강제 차단즉시 (서버 세션 삭제)Access 만료까지 유효, 막으려면 차단 목록 → 결국 서버 상태 필요
탈취 위험HttpOnly → JS가 읽지 못함화면 코드가 토큰 보유 → XSS 한 번에 유출 가능
구현 · 유지보수Spring Security + Spring Session 기본 기능발급 · 회전 · 재사용 탐지 · 동시 갱신 충돌 처리 직접 구현
우리 앱 특유 위험—메인 창 + 요약 위젯이 동시에 갱신 → 회전 충돌로 정상 사용자 로그아웃
추가 공수약 2~3인일약 4~6인일
JWT를 쓰는 곳은 딱 한 곳 — 화면공유 서버(LiveKit) 입장권. LiveKit은 우리 Redis 세션을 볼 수 없으므로, 이미 세션으로 로그인한 사용자에게 Spring이 짧은 유효시간 · 방 · 권한이 담긴 JWT를 그때그때 발급한다. 만료되면 세션으로 다시 받으므로 여기에도 리프레시 토큰은 없다. → "JWT가 맞는 곳(외부 서버 검증)과 세션이 맞는 곳(우리 API)을 구분"

3. OWASP 세션 관리 기준 점검 (2026-11-16 실측)

OWASP 기준상태근거 (실제 확인 결과)
세션 번호 64비트 이상 무작위충족Spring Session UUID (36자, 무작위 122비트)
HttpOnly (XSS 탈취 방지, 필수)충족응답 헤더 Set-Cookie: SESSION=…; HttpOnly
SameSite (Strict 또는 Lax)충족 (Lax)응답 헤더 SameSite=Lax
Secure (HTTPS 전용)조건부HTTPS 배포 시 nginx의 X-Forwarded-Proto로 자동 적용. 로컬 http에서는 확인 불가 → 배포 때 점검
로그인 시 세션 번호 재발급 (필수)충족소셜 로그인은 Spring Security 기본, 개발용 로그인은 changeSessionId()
로그아웃 시 서버에서 무효화충족로그아웃 전 Redis 키 존재(1) → 후 삭제(0). 예전 쿠키로 재요청 시 401
CSRF 방어 (RFC 10017: 필수)충족사용자 정의 헤더 X-XSRF-TOKEN + SameSite. 토큰 없는 POST는 403
유휴 시간 제한보완 필요현재 8시간 → 학습 서비스 기준 1~2시간 권장
절대 시간 제한미구현Spring Session 기본 기능에 없음 → 필터로 추가 필요
SameSite를 Strict가 아닌 Lax로 둔 이유 — RFC 10017은 Strict를 "권장(SHOULD)"하지만, Strict면 카카오·네이버 로그인 후 우리 사이트로 돌아오는 요청에 세션 쿠키가 붙지 않아 로그인이 깨진다. Lax는 OWASP가 허용하는 값이며, CSRF는 사용자 정의 헤더로 별도 방어한다.

4. 남은 보완 사항

#항목방법난이도
1유휴 시간 단축spring.session.timeout: 2h (설정 한 줄)매우 낮음
2절대 시간 제한 추가로그인 후 12시간이 지나면 활동 중이어도 재로그인 (세션 생성 시각 검사 필터 + 테스트)낮음
3HTTPS 배포 시 Secure 확인Cloudflare Tunnel 연결 후 응답 헤더에 Secure 포함 여부를 배포 체크리스트로 점검낮음
4(선택) 모든 기기 로그아웃Spring Session의 사용자별 세션 조회로 한 번에 무효화 (OWASP: 같은 인증 세션 일괄 폐기)중간

1~3을 마치면 위 OWASP 세션 점검표의 모든 항목을 충족한다.

5. 발표 · 면접용 요약

"브라우저와 데스크톱 앱이 모두 웹 기술이라 IETF RFC 10017이 가장 안전하다고 권하는 BFF 패턴을 택했습니다. 토큰은 서버에만 두고 클라이언트에는 HttpOnly 세션 쿠키만 줘서 탈취할 토큰 자체가 없게 했습니다. 리프레시 토큰은 RFC 9700에 따라 클라이언트에 줄 경우 회전이나 발신자 제한이 필수인데, 우리는 토큰을 클라이언트에 주지 않아 그 위험과 복잡도를 원천적으로 없앴습니다. 대신 세션은 OWASP 기준(HttpOnly, SameSite, 로그인 시 재발급, 서버 측 무효화, CSRF 헤더)으로 보호했고, 우리 세션을 볼 수 없는 외부 미디어 서버(LiveKit)에만 짧은 JWT를 발급합니다."
